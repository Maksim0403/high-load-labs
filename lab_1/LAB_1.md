# 1. Піковий сценарій навантаження (High-Load Scenario)

## Назва сценарію
Масове завантаження фото підтвердження доставки — `POST /delivery-photos`

## Контекст
Наприкінці робочого дня N водіїв (оцінка: 150–300 одночасних користувачів)
синхронно завершують маршрути й надсилають фото підтвердження доставки через
мобільний застосунок. Усі запити приходять у вузькому часовому вікні
(закінчення зміни), що створює пікове навантаження на бекенд.

## Ланцюжок виконання запиту
Кожен виклик `delivery_photo_service.upload_photo()` виконує таку
послідовність операцій в межах **одного** HTTP request-response циклу:

1. Повне зчитування файлу (до 10 МБ) в оперативну пам'ять процесу бекенду —
   `contents = await file.read()`.
2. Валідація MIME-типу (`image/jpeg`, `image/png`, `image/webp`) та розміру
   файлу.
3. Синхронне вивантаження бінарних даних у SeaweedFS через S3 API —
   `s3_client.upload_file()`. Це зовнішній мережевий I/O-виклик, що блокує
   обробку запиту до завершення.
4. Запис метаданих фото в PostgreSQL — `crud_photo.create_photo()`.
5. Повторний виклик до S3 для генерації presigned URL —
   `s3_client.get_presigned_url()`.

## Чому саме цей сценарій є піковим
Типові CRUD-операції системи (наприклад, `GET /orders/{id}` — один `SELECT`
за первинним ключем) виконуються за одиниці мілісекунд і навантажують лише
одну підсистему (СУБД). Сценарій завантаження фото натомість одночасно
навантажує:

| Ресурс           | Де саме                                              |
|-------------------|-------------------------------------------------------|
| Пам'ять процесу   | буферизація всього файлу перед відправкою в S3         |
| Мережевий I/O     | подвійний round-trip до зовнішнього S3-сховища          |
| Дисковий I/O      | запис метаданих у PostgreSQL                            |
| Конкурентність    | увесь ланцюжок виконується синхронно, без черги/фонової обробки |

Через це операція є найресурсоємнішою точкою системи під навантаженням і
обрана як предмет подальшого аналізу вузьких місць (розділ 2.5).

## Параметри сценарію для оцінки навантаження
- Одночасних користувачів: 150–300
- Розмір файлу: 3–10 МБ (ліміт `MAX_FILE_SIZE = 10 MB`)
- Очікуваний пік RPS: 20–50 запитів/с у вузькому вікні (кінець зміни)
- Тип операції: write-heavy, I/O-bound (мережа + диск), без кешування
