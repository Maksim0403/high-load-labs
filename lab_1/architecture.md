# Архітектурний захист

## 1. Обґрунтування архітектурного стилю

Система побудована за **шаруватою (layered) архітектурою** з чітким
поділом на контейнери (див. C4 container diagram, розділ 2):

```
Client → Nginx (API Gateway) → Frontend / Backend → PostgreSQL / SeaweedFS (S3)
```

- **Nginx** виступає єдиною точкою входу (API Gateway): приховує внутрішню
  топологію мережі, маршрутизує `/` на Frontend, `/api/`, `/docs`,
  `/openapi.json`, `/redoc` — на Backend. Це дозволяє в майбутньому
  додати TLS-термінацію, rate limiting чи балансування навантаження між
  кількома інстансами backend без зміни коду застосунку.
- **Backend (FastAPI)** — окремий сервісний шар, stateless (стан
  зберігається лише в БД і токенах), що є передумовою для горизонтального
  масштабування (можна підняти кілька реплік backend за Nginx без змін
  у коді).
- **PostgreSQL** — єдине первинне сховище стану (single source of truth),
  винесене в окремий контейнер з іменованим volume — відокремлення шару
  даних від шару обчислень.
- **SeaweedFS (S3-сумісне сховище)** — окремий сервіс для бінарних
  об'єктів (фото доставки), винесений із backend і з БД. Це свідоме
  архітектурне рішення: великі бінарні файли не зберігаються ні в
  реляційній БД (немає роздування таблиць/BLOB), ні на диску контейнера
  backend (немає прив'язки стану до конкретного інстансу — важливо для
  масштабування).

## 2. Доцільність декомпозиції

Backend всередині розділений на прошарки за відповідальністю
(`api/routes` → `services` → `crud` → `models`):

- **routes** — тільки HTTP-контракт (валідація вхідних даних через
  Pydantic-схеми, авторизація через `Depends`);
- **services** — бізнес-логіка (наприклад, `order_service` перевіряє
  правила переходу статусів замовлення, `invoice_service` рахує
  агрегати);
- **crud** — ізольований шар доступу до даних (SQL-запити через
  SQLAlchemy);
- **models / schemas** — розділення ORM-моделей (SQLModel) і
  API-контрактів (Pydantic schemas) — зміна внутрішньої структури БД не
  обов'язково ламає зовнішній API.

Це знижує зв'язність (coupling): бізнес-логіку можна тестувати без HTTP-
шару (див. `backend/tests/`), а SQL-шар можна змінювати, не чіпаючи
контролери.

## 3. Дотримання REST-стандартів

- Ресурсні URL, а не RPC-стиль: `/api/v1/orders`, `/api/v1/orders/{id}`,
  `/api/v1/vehicles`, а не `/getOrders` чи `/createOrder`.
- HTTP-методи відповідають семантиці CRUD: `POST` — створення,
  `GET` — читання, `PATCH` — часткове оновлення, `DELETE` — видалення.
- Версіонування API винесено в префікс `/api/v1` — дозволяє в
  майбутньому ввести `/api/v2` без поломки існуючих клієнтів.
- Коди відповідей відповідають семантиці (`201` при створенні, `404` при
  відсутності ресурсу, `403` при відмові в доступі — видно в
  `order_service.py`).
- Самодокументованість через OpenAPI/Swagger (`/docs`, `/openapi.json`,
  `/redoc`), що є прямим наслідком використання FastAPI + Pydantic-схем.

## 4. Рішення щодо масштабованості

**Що вже закладено:**
- Backend stateless — можна масштабувати горизонтально (кілька реплік за
  Nginx/балансувальником) без зміни коду.
- Розділення сховища бінарних об'єктів (S3/SeaweedFS) і реляційних даних
  (PostgreSQL) — кожен шар масштабується окремо і незалежно.
- Асинхронний backend (FastAPI + `AsyncSession`, async I/O до БД і S3) —
  дозволяє обробляти більше одночасних I/O-bound запитів на один процес
  порівняно з синхронною моделлю.

**Що є обмеженням поточної реалізації (і пов'язано з bottleneck-аналізом,
розділ 3):**
- PostgreSQL — єдина точка запису (single point), без реплік для читання
  (read replicas) і без партиціонування великих таблиць.
- Відсутність черги повідомлень — фонові/важкі операції (наприклад,
  завантаження фото) виконуються синхронно в request-циклі, що обмежує
  масштабованість саме цієї операції без додавання черги (наприклад,
  Celery + Redis/RabbitMQ) у майбутніх ітераціях.
- Пул з'єднань до БД налаштований на дефолтних значеннях SQLAlchemy — для
  реального масштабування потребує явного тюнінгу `pool_size` /
  `max_overflow` відповідно до очікуваного RPS.

## 5. Відтворюваність (запуск «із коробки»)

Перевірено холодним стартом (`docker-compose down -v && docker-compose up
-d`) з чистого стану — після створення `.env.backend`, `.env.db`,
`.env.pgadmin` на основі `.env.*.example`-файлів система піднімається без
помилок середовища. Персистентність даних БД підтверджена іменованим
Docker volume `postgres_data`, що зберігає стан між перезапусками
контейнера `db`.
