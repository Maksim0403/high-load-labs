# 2.5. Аналіз потенційних вузьких місць (Bottleneck Analysis)


## 1. Відсутність пагінації у вибірках замовлень

**Компонент / Операція / Запит:**
`GET /orders`, `GET /dashboard/orders` — `crud/order.py: get_orders()`

**Причина (Root Cause):**
Запит формується без `LIMIT`/`OFFSET` — пагінація відсутня. При зростанні
таблиці `orders` кожен виклик повертає весь набір рядків, що задовольняє
фільтр, цілком.

**Симптоматика та прояв:**
- Лінійне зростання часу відповіді та обсягу серіалізованих даних
  пропорційно кількості замовлень у БД.
- Падіння throughput (RPS) при паралельних запитах через зростання
  навантаження CPU на серіалізацію JSON.
- Зростання Latency p95/p99 саме на цьому ендпоінті швидше, ніж на інших.

## 2. Відсутність індексів на колонках фільтрації / JOIN

**Компонент / Операція / Запит:**
Таблиці `orders`, `routes`, `shipments` — колонки `owner_id`, `order_id`,
`driver_id`, `status` (`models/order.py`, `models/route.py`,
`models/shipment.py`)

**Причина (Root Cause):**
Ці колонки використовуються у `WHERE`-умовах і як зовнішні ключі для
`JOIN`, але не мають явного індексу (`index=True` відсутнє в жодній
моделі).

**Симптоматика та прояв:**
- PostgreSQL виконує Sequential Scan замість Index Scan.
- Зростання I/O wait і CPU на контейнері `db` пропорційно розміру таблиці.
- Погіршення p99 latency саме на фільтруючих і агрегаційних запитах, тоді
  як прості вибірки за первинним ключем лишаються швидкими — характерна
  ознака саме відсутності індексів, а не загальної нестачі ресурсів.

## 3. Синхронне завантаження фото в S3 без черги

**Компонент / Операція / Запит:**
`POST /delivery-photos` — `delivery_photo_service.upload_photo()`

**Причина (Root Cause):**
Вивантаження файлу в SeaweedFS виконується всередині одного
request-response циклу backend-процесу, без черги повідомлень чи фонової
задачі (Celery/RQ тощо в проєкті немає). Файл попередньо повністю
буферизується в пам'яті (`await file.read()`).

**Симптоматика та прояв:**
- Вичерпання пулу воркерів/конекшнів ASGI-сервера при масовому
  одночасному завантаженні фото (Connection/Worker Pool Exhaustion).
- Зростання RSS-пам'яті процесу пропорційно кількості одночасних
  завантажень × розмір файлу.
- Побічний ефект: деградація latency навіть на непов'язаних ендпоінтах
  (`GET /orders`), бо вони конкурують за той самий обмежений пул
  воркерів.

## 4. Обмежений пул з'єднань до БД + надлишкове логування

**Компонент / Операція / Запит:**
SQLAlchemy `AsyncEngine` — `db/session.py`

**Причина (Root Cause):**
`create_async_engine(settings.DATABASE_URL, echo=True)` створюється без
явних `pool_size`/`max_overflow` — використовуються дефолти SQLAlchemy
(`pool_size=5`, `max_overflow=10`, разом лише 15 одночасних з'єднань до
Postgres). Додатково `echo=True` змушує рушій логувати кожен SQL-запит,
що додає CPU-накладні витрати при високому RPS.

**Симптоматика та прояв:**
- При кількості одночасних запитів понад 15 — помилки на кшталт
  `QueuePool limit exceeded` / timeout очікування вільного з'єднання.
- Connection Pool Exhaustion як пряма причина відмов під навантаженням.
  - Додаткове зростання латентності через накладні витрати логування
    (`echo=True`) у production-подібному навантаженні.
